# What Freyr should learn from Attio and other sales platforms

Researched October 2, 2026. Status: research complete; recommendations only, no feature implementation. The user’s new QA campaign excludes Agent questions and paid AI calls.

## Recommendation

Improve three existing workflows before adding another large feature: a meeting preparation page with evidence, a daily work queue with clear reasons, and opportunity reviews that expose missing information. Freyr already has customers, contacts, meetings, offerings/materials, opportunity reviews, health scores and reminders. The opportunity is to connect and verify those pieces rather than duplicate them with new chat screens.

This is a comparison of 12 relevant product families, not a market-share ranking or a hands-on certification. Vendor capabilities below are documented claims from primary sources checked today. Plan, region and rollout eligibility need checking before any procurement. No trial accounts, demos, enrichment jobs, outreach or paid provider calls were started. Clari and Salesloft are grouped because the current Clari product link redirects to Salesloft’s platform, which includes Clari Forecast.

## What to take specifically from Attio

Attio’s useful pattern is contextual work: an account page, call or selected record can become the starting point for a question or action. Its documentation also describes reviewing note changes before acceptance and using the viewer’s permissions. These are more relevant to Freyr than copying surface styling. [Ask Attio documentation](https://attio.com/help/reference/attio-ai/ask-attio/chat-with-ask-attio)

Freyr already has a contextual dock, selected-record pills, source retrieval and action proposals. The recommendation is to make those existing pieces dependable and consistent with the underlying record pages, not introduce another assistant. A shared prompt library could later offer focused tasks such as “prepare this account review” or “compare these approved materials,” but those should operate on selected IDs and visible sources rather than guess which similarly named entity the user means.

## What already exists, and what is not verified

Repository inspection found reminder buckets and account health helpers, opportunity review UI, record selection, document passages and proposal code. Their existence is not proof that every role or edge case works. The durable role audit has known policy mismatches and incomplete UI cells. These proposals must be reconciled with that audit before implementation.

Do not expand autonomous outreach, add speculative lead scoring, run video analysis on every upload, or switch to a cheaper model on an assumed quality improvement. Those introduce new recurring cost or behavior without addressing the app’s immediate reliability needs. In the current campaign the user specifically prohibited Agent queries; all recommended AI behavior remains research-only.

## Verification and next action

Sources were checked as public documentation, not by purchasing or using each platform. Vendor ROI percentages and homepage testimonials were not used to rank options. Public product pages can describe staged rollouts; feature availability must be reconfirmed if a buying/build decision depends on it.

Research is now complete enough for a product decision. Next work is the user-authorized non-Agent development audit: actual authenticated privilege sessions, page and control interactions, server-side refusals, disposable fixture cleanup and a continuously updated coverage ledger. No speculative features from this report should be built during that audit.
